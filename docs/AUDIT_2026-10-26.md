### P1-4 — Passage text can still be model output cached as Scripture

`BibleService.fetchVerse` tries `https://bible-api.com` (public-domain-friendly ids: `kjv`, `web`, `bbe`, `asv`). On any failure it calls the same chat backend (`mode: verse_lookup`) and asks it to “Provide ONLY the exact Scripture text,” then stores that string in the in-memory cache under the verse key. `AIService` sends that string back as `Verse text:` for every study mode.

If bible-api.com is down, the user is shown model output as Scripture, and the study answer is conditioned on it. Non-200 and transport errors on the primary fetch are swallowed (`try?`), so a total failure surfaces as `BibleServiceError.verseNotFound` (“Verse not found”) rather than an offline state. `AIService` maps every non-200 to “Server returned an error.” There is no retry on the chat call.

Reference chips are in better shape than the passage itself. After the model replies, `verifyReferences` checks each extracted reference against bible-api.com. A 400/404 omits the reference. A transport failure or non-200 leaves it visible and labeled unavailable. That check does not run on the cached fallback string used as the passage.

The client prompt for non-summary modes is one sentence plus “include verse numbers.” It does not mention original languages, Augustine, Lewis, Wright, Spurgeon, or MacArthur. Distinct modes are the `mode` string sent to `https://scripture-copilot-rust.vercel.app/api/chat`. The system prompt is not in this repo.

`HomeViewModel.loadDailyVerse` displays `daily_content.passage` verbatim when the Supabase row is present. Confirm those rows are a public-domain translation. This audit did not read the table.

Onboarding offers a second, live, unscoped call. `OnboardingView.fetchOnboardingInsight` POSTs `{ "messages": [...] }`. `AIService` POSTs `{ "message", "passage", "mode", "history" }`. If the server only understands the latter, the aha screen falls through to `getPrewrittenInsight`, which states contested lexical claims as fact (Elohim as a Trinity hint, `bara` never used of humans, `ischyo` as “strength to endure”) and does not show the disclaimer that `AIResponseView` shows (“AI-generated study aid…”). That screen is on the live path: welcome → aha → attribution.

### P1-5 — The daily limit and the chat endpoint are client-side

`UsageService` stores `usageDate` / `usageCount` in `UserDefaults`. `canAsk` runs before the request; `recordQuestion` runs only after a stream finishes without throw. Consequences:

- Reinstall, or a changed device date, resets the counter. `Date.dayString` uses the device timezone, not an account.
- Nothing in `AIService` sends a user id, receipt, or remaining-quota header. The URL is unauthenticated from this client.
- Two overlapping `selectMode` calls can both pass `canAsk` before either increments. The view model cancels the previous task, which usually avoids this, but the service itself is not serialized.
- A 200 with an empty body still counts as a question.
- The onboarding aha call does not call `recordQuestion`.

The limit matches the public listing (3). It is not an entitlement.

### P1-6 — A privacy manifest exists; “no data collected” is still false

`BibleCopilot/PrivacyInfo.xcprivacy` is in the app target. `NSPrivacyTracking` is false. Accessed API types declare UserDefaults (`CA92.1`). Collected data types cover name, email, user id, device id (analytics, linked, not tracking), purchase history, product interaction, and other user content.

What the binary actually does, which the manifest is trying to describe:

- `AnalyticsService` POSTs `device_id` (random UUID in `UserDefaults`, not IDFA), `session_id`, `app_version`, event name, and `onboarding_heard_about` when set. No `NSUserTrackingUsageDescription`, no ATT prompt, no `ASIdentifierManager`. That is first-party analytics, not cross-app tracking, and it is data collection.
- Sign in with Apple or email stores the access token, refresh token, user id, display name, and email in the Keychain (`AuthService`, `KeychainService`) and upserts email onto `profiles`.
- Photo library usage strings exist for TikTok share cards (`Info.plist`).
- `SentryService` sets `sendDefaultPii = false`. It no-ops unless `SentryDSN` starts with `https://`.

`metadata/app_store_metadata.md` still says “No data collected.” Pasting that sentence would contradict this manifest and the code. Match the App Store privacy nutrition label to the manifest before 2.4.8 leaves review. This audit did not open App Store Connect to compare the label.

`KeychainService` does not set `kSecAttrAccessible`. The default allows the items in encrypted backups. Tokens should be `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` (guidance only).

Sign-in `print` of name/email is inside `#if DEBUG`. Release builds do not log that line.

ATS: `Info.plist` has no `NSAppTransportSecurity` exceptions. All endpoints found are `https://`. `ITSAppUsesNonExemptEncryption` is false, which matches “HTTPS only.”

### P2-3 — Reliability nits

- `AIService.streamTopicResponse` returns on cancellation without `continuation.finish()`. `streamResponse` does finish. A cancelled topic stream can hang the consumer.
- `askFollowUp` appends the user turn to `chatHistory` before the stream succeeds. A failure leaves an orphan user turn and still does not increment usage. The next attempt sends a duplicated question.
- `SubscriptionService.isPro` stays false until `checkSubscriptionStatus` finishes. A Pro user can be shown the paywall for a moment at launch. Status uses `Transaction.currentEntitlements` and rejects `.unverified`. Pending (Ask to Buy) does not set `isPro`.
- `UsageService.usedToday` does not call `resetIfNewDay`. A process left open past midnight shows yesterday’s count until the next `canAsk` or `recordQuestion`. The paywall trigger compares `usedToday` to 3, so that stale count can change the headline.
- `ReviewService` requests a review at studies 3, 10, and 30. Study 3 is also the moment the free user has just used the last question. The system may show a review dialog and the next tap opens the paywall.
- Force-unwraps found are `URL(string:)` on string literals (`AIService`, `AnalyticsService`, `AuthService`, legal links). They do not depend on user input.

### P2-4 — Analytics and attribution

Event names in `AnalyticsEvent` include `app_open`, `paywall_view`, `trial_start_tap`, `purchase_success`, `purchase_failed`, restore attempt events, `question_asked`, `limit_hit`, and `plan_selected`. `paywall_view` includes `trigger` `free_limit` vs `manual_upgrade` based on `usedToday >= 3`, plus `copy_version` and `trial_eligibility`.

Gaps:

- `trial_start_tap` fires when the button is tapped, including cancel and failed StoreKit loads. It is not a trial start.
- `purchase_success` fires when `isPro` becomes true. It does not record whether an intro offer was applied, the price, or the country.
- No Apple Ads `pt` / `ct` parameters on post-#7 `main`. Share text does not include an App Store campaign link. Those links were part of PR #4’s design. They are not in this tree. Do not recover them by merging PR #4. Start that work from this `main`.
- Attribution that does exist is the optional self-report `onboarding_heard_about`, copied onto later events. It is not SKAdNetwork and not an ASA campaign token.

## What is in good shape

- Bundle id `com.scripturecopilot.app` is consistent across plist, pbxproj, `project.yml`, `app.json`, and the public lookup.
- The archived marketing version in `project.pbxproj` is 2.4.8 (134), the same tree Apple has in review as build 134.
